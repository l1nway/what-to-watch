# Cloud Functions

Firestore-триггеры и callable-функции проекта. Регион всех триггеров — `europe-central2`.

Инициализация Admin SDK вынесена в `src/firebase.ts` (`db`, `region`) — она должна выполняться до первого `getFirestore()` в любом модуле, поэтому оба файла с функциями импортируют `db` оттуда, а не инициализируют приложение сами.

## activity-feed

Лента действий группы: `/groups/{groupId}/activity/{eventId}`. Пишется только бэкендом из триггеров `onGroupActivityFeed` (`groups/{groupId}`), `onListActivityFeed` (`lists/{listId}`), `onInviteActivityFeed` (`invites/{inviteId}`) и `onUserActivityFeed` (`users/{userId}`), файл `src/activity.ts`.

Документ события:

| Поле | Значение |
| --- | --- |
| `timestamp` | `FieldValue.serverTimestamp()` |
| `userId` | автор действия (см. «Кто автор») или `'system'`, если автор неизвестен |
| `type` | тип события из таблицы ниже |
| `details` | произвольный объект: `oldName`, `newName`, `memberId`, `listId`, `listName`, `movieId`, `status`, `role`, `avatarUrl`, `name`, `email` |

### Типы событий

Теги синхронизированы с клиентским словарём текстов ленты (`ActivityType`) — триггер не пишет ничего, для чего там нет описания.

Группа (`onGroupActivityFeed`):

- `group_created` — `{name}`, при создании документа группы (`before` отсутствует).
- `group_renamed` — `{oldName, newName}`.
- `member_joined` — `{memberId, role}`, `userId` = вошедший. `role` берётся из того же батча: если участник одновременно попал в `editors`, это `'editor'`, иначе `'viewer'`.
- `member_left` / `member_kicked` — `{memberId, avatarUrl, name}`. `member_left`, когда `updatedBy` совпадает с выбывшим; `member_kicked`, когда его удалил кто-то другой (`userId` = инициатор). `avatarUrl`/`name` — снимок профиля (`users/{uid}.photoURL` и `displayName`/`name`/`email` по порядку), сделанный в момент выхода: после ухода из группы участник может стать нечитаемым для тех, кто видит ленту, поэтому его данные не резолвятся заново при чтении.
- `member_role_changed` — `{memberId, role}`, `role` — `'editor'` или `'viewer'`. Пишется **только** для участников, состав которых не менялся: вход и кик уже несут роль в своих событиях, иначе один батч давал бы два события об одном человеке.

Список (`onListActivityFeed`), пишется в ленту той группы, к которой список привязан; личные списки (`groupId === null`) ленту не наполняют:

- `list_created` — `{listId, listName}`, при создании документа списка сразу внутри группы (`before` отсутствует).
- `list_deleted` — `{listId, listName}`, при удалении документа списка (`after` отсутствует), в ленту группы, к которой список был привязан.
- `list_added` / `list_removed` — `{listId, listName}`. Срабатывают на смену `groupId` у существующего документа (список отвязан от одной группы и/или привязан к другой), а не на его создание или удаление — те покрыты `list_created`/`list_deleted`.
- `list_renamed` — `{listId, oldName, newName}`.
- `movie_added` / `movie_removed` — `{listId, listName, movieId, status}`. Тег один для фильмов и сериалов (поле `type` элемента в событие не попадает); смена `status` у уже добавленного фильма отдельного события не пишет.

Профиль (`onUserActivityFeed`), пишется во все группы пользователя сразу:

- `member_profile_updated` — `{memberId, avatarUrl, name}`, `userId` = сам пользователь. Срабатывает на смену `photoURL` и/или `displayName`/`name`/`email` (та же логика выбора имени, что у `member_left`/`member_kicked`) в `users/{userId}`. Список групп для рассылки — `users/{userId}.groups`, синхронизируемый `onGroupSync` в `src/index.ts`; событие пишется в каждую группу из этого массива одним батчем. Создание документа пользователя (`before` отсутствует) событий не порождает.

Приглашения (`onInviteActivityFeed`), пишется в ленту группы, к которой инвайт привязан (`invites/{inviteId}.groupId`):

- `invite_created` — `{email, role}`, при создании документа инвайта (`before` отсутствует, `status === 'pending'`). `userId` = `senderId` инвайта, а не `updatedBy` — на создании автора приносит другое поле (см. «Кто автор»). Повторная отправка (`merge`-перезапись того же `generic_{groupId}` или `{email}_{groupId}`) документа не создаёт, поэтому события не дублирует.
- `invite_rejected` — `{email}`, `userId` = получатель, отклонивший приглашение. Пишется на удаление документа инвайта (`after` отсутствует), и только если перед удалением получатель успел проставить `{status: 'rejected', updatedBy}` (`app/settings/useInvites.ts: rejectInvite`) — без этой метки удаление инвайта неотличимо от принятия или ручной чистки, поэтому событие не пишется.

Принятие инвайта отдельного события не имеет: `acceptInvite`/`invite.tsx` в одном действии добавляют пользователя в `groups.members`, и это уже покрыто `member_joined` из `onGroupActivityFeed` — повторять его как `invite_accepted` было бы дублированием одного действия. Отзыв инвайта отправителем и его протухание сейчас не трекаются: возможности отозвать отправленный инвайт в приложении нет, а протухание — это истечение времени, а не запись в базу, и обычным Firestore-триггером не ловится (нужна была бы отдельная scheduled-функция) — решено, что для ленты активности это не нужно.

### Как вычисляется разница

Фильмы лежат массивом в `lists/{listId}.movies` (`{id, status, type}`), подколлекции нет. Триггер строит из `before.movies` и `after.movies` две `Map` с ключом `id:type` и сравнивает их: ключ есть только в `after` — добавление, только в `before` — удаление. Массивы `members` и `editors` группы сравниваются напрямую.

При смене `groupId` у живого документа списка содержимое не диффится: иначе переезд списка выдал бы «добавил фильм» во всех лентах сразу. Переезд — это ровно два события: `list_removed` в старой группе и `list_added` в новой.

### Кто автор (`updatedBy`)

В Firestore-триггерах нет `context.auth` — событие приходит от базы, а не от пользователя. Автора приносит сам клиент: **каждая запись в `groups/*` и `lists/*` содержит поле `updatedBy` с `auth.uid` пишущего**, и триггер читает его из `after` (для удаления — из `before`). Точки записи на фронтенде: `app/dashboard/useDashboard.tsx`, `app/list/useList.tsx`, `app/list/movieSearch.tsx`, `app/list/movieClarify.tsx`, `app/invite/invite.tsx`, `app/settings/useInvites.ts`.

Инвайты (`invites/*`) этот же приём используют только частично: на создании автор — поле `senderId` (инвайт пишет его отправитель, `updatedBy` там ещё нет), а `updatedBy` появляется только при отклонении, как метка, проставленная получателем непосредственно перед удалением документа.

Следствия:

- Поле подделываемо на клиенте, поэтому его обязан проверять Firestore Rules: `request.resource.data.updatedBy == request.auth.uid` на любой записи в `groups` и `lists`. Без этого правила автор в ленте — то, что прислал клиент.
- Удаление документа поле проставить не может, поэтому `deleteList` сначала штампует `updatedBy`, потом удаляет. Для удалённого не нами документа автором будет последний писавший.
- Записи самого бэкенда (`touchList`) `updatedBy` не меняют — и не порождают событий, потому что не меняют ни имя, ни `groupId`, ни состав фильмов.

### Инварианты

- ID документа события детерминирован: `${event.id}_${i}`, где `event.id` — идентификатор CloudEvent. Повторная доставка (`retry: true`) перезаписывает те же документы, а не удваивает ленту.
- Перед записью проверяется, что группа ещё существует (`db.getAll`): удаление группы отвязывает её списки тем же батчем, и без проверки мы бы воскресили подколлекцию мёртвой группы. Из-за этой же проверки `group_created` пишется штатно (группа уже существует к моменту срабатывания триггера), а удаление самой группы событий не порождает — лента удаляется вместе с группой (подколлекции Firestore при удалении родителя не чистятся — если нужен полный клинап, его делает отдельная рекурсивная функция, сейчас её нет).
- Все события одной записи коммитятся одним батчем.

## list-updated-tracking

Поле `lists/{listId}.updated` — серверная отметка времени последнего действия со списком. Пишется **только бэкендом**, фронтенд его не трогает и не читает.

Отметка обновляется, если изменилось хоть что-то из «отслеживаемой подписи» документа списка:

- `name` (создание и переименование),
- `groupId` (список добавлен в группу / убран из неё / группа удалена),
- `movies` — множество фильмов, нормализованное как `id:type:status` и отсортированное (добавление, удаление, смена статуса фильма).

Функции:

- `onListActivity` (`lists/{listId}`) — основной триггер. Сравнивает подпись `before` и `after`; если они совпадают, выход без записи. Это и есть защита от бесконечного цикла: собственная запись `updated` подпись не меняет, поэтому повторный запуск триггера сразу завершается. Удаление списка отметку не пишет.
- `onGroupListsActivity` (`groups/{groupId}`) — подстраховка на случай записи, которая меняет только массив `groups.lists`, не трогая `lists.groupId`. Штампует все списки, появившиеся в массиве или исчезнувшие из него. Если такая запись идёт в одном батче с обновлением `lists.groupId`, список может быть проштампован дважды — это безопасно, лишняя запись подпись не меняет.

Инварианты:

- Оба триггера объявлены с `retry: true`, поэтому при сбое событие доставляется повторно — отметка не теряется.
- Значение — `FieldValue.serverTimestamp()`, то есть абсолютный момент времени (Firestore `Timestamp`, UTC). Он не зависит ни от часового пояса клиента, ни от его системных часов; при чтении форматируется под нужный пояс.
- Список, удалённый между событием и записью, приводит к ошибке `NOT_FOUND` (код 5) — она гасится, остальные ошибки пробрасываются, чтобы сработал retry.

## invite-push

`onInvitePush` (`invites/{inviteId}`) — отправляет push через [Expo Push API](https://exp.host/--/api/v2/push/send) при создании персонального инвайта в группу.

Условия отправки:

- у документа есть поле `email` (у generic-инвайтов `generic_{groupId}` его нет — пушить некому);
- `status === 'pending'`;
- это создание документа либо повторная отправка. Клиент пишет инвайты через `batch.set(..., {merge: true})`, поэтому повторное приглашение той же пары `email+groupId` перезаписывает существующий документ. Признак повторной отправки — изменившийся `createdAt`; если `before.status` уже был `pending` и `createdAt` не менялся, это посторонняя правка и push не шлётся.

Получателя ищем запросом `users where email == invite.email` (лимит 1) и берём поле `pushToken` (Expo Push Token, регистрируется клиентом через expo-notifications). Токена нет — штатная ситуация (нет permission или не мобильное устройство), выходим молча.

Тело сообщения:

- `categoryId: 'invite'` — **обязательно ровно эта строка**. На клиенте зарегистрирована notification category `invite` с действиями `accept` («Accept») и `reject` («Decline»), обе с `opensAppToForeground: false`. Без совпадения идентификатора кнопки на уведомлении не появятся ни на iOS, ни на Android.
- `data: {type, token, groupId}`, где `token` — поле `token` самого инвайта. По нажатию Accept/Decline клиент находит инвайт запросом `where('token', '==', token)` и обрабатывает его сам (`src/features/settings/pushInviteActions.ts` в мобильном репозитории). Сервер колбэка о нажатии не получает и ничего дополнительно не делает.

Ответ Expo разбирается по тикетам: тикет со `status: 'error'` логируется, а при `details.error === 'DeviceNotRegistered'` токен обнуляется — `users/{uid}` `{pushToken: null}` с `{merge: true}`.

Ошибки сети и API только логируются: недоставленный push не должен ронять функцию и провоцировать повторную доставку события.

## email-sign-in-sync

`syncEmailOnSignIn` (callable) — страховка на случай, когда пользователь подтверждает смену почты (переходит по ссылке из письма) **не будучи залогинен** в приложении: тогда `emailAction.tsx` не выполняется и меняется только Auth-запись, а `users/{uid}.email`/`emailStatus`/`pendingEmail` остаются старыми. Клиентское самолечение в `useProfile.ts` эту рассинхронизацию не чинит, потому что монтируется только на экране настроек и может так никогда не открыться.

Изначально планировался как `beforeSignIn`-блокирующая функция (единственный Auth-триггер, реагирующий на уже существующего пользователя — обычного `onUpdate`-события для Auth не существует ни в v1, ни в v2), но блокирующие функции доступны только проектам, апгрейднутым до Identity Platform (GCIP); деплой падал с `OPERATION_NOT_ALLOWED`. Апгрейд до GCIP меняет тарификацию всего Auth в проекте, поэтому вместо него — callable, который клиент дёргает сам сразу после входа.

Вызывается из `app/components/authProvider.tsx` при каждом появлении `user` (реагирует на смену `user?.uid`) — это корневой провайдер авторизации, смонтированный независимо от того, какой экран открыт, поэтому вызов происходит при любом входе, а не только при заходе в настройки.

Логика (зеркалит самолечение `useProfile.ts`):

- `uid` берётся из `request.auth` (проверенный токен), а актуальный email читается через Admin SDK (`getAuth().getUser(uid)`) — email из тела запроса не используется и клиенту не доверяется;
- если `users/{uid}.email` уже совпадает с Auth-email — выход без записи;
- иначе `email` в документе всегда подтягивается к Auth-email;
- если при этом `pendingEmail` документа совпадал с новым Auth-email (смена реально была инициирована и подтверждена), дополнительно проставляется `emailStatus: 'verified'` и `pendingEmail` удаляется.

Ошибка вызова на клиенте гасится (`.catch(() => {})`) — сбой синхронизации не должен мешать входу в приложение.

## Остальные функции

- `onGroupActivityFeed`, `onListActivityFeed`, `onInviteActivityFeed`, `onUserActivityFeed` — лента действий группы, см. [activity-feed](#activity-feed).
- `onUserCreate` — создаёт документ `users/{uid}` при регистрации.
- `onGroupSync` — синхронизирует массив `users/{uid}.groups` с `groups/{groupId}.members`.
- `syncEmailOnSignIn` — см. [email-sign-in-sync](#email-sign-in-sync).
- `searchMovies`, `getMovieDetails` — прокси к TMDB (секрет `TMDB_KEY`).
- `getAiRecommendations` — подбор похожих фильмов через Gemini (секрет `GEMINI_API_KEY`) с недельным кэшем в `movie_recommendations_cache`.
